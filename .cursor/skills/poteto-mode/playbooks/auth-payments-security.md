### Auth, payments, and security

**You own the trust boundary. Write down what an attacker wants, then prove they cannot get it. Prove payments in the provider's sandbox, never with real money.**

1. Write a five-line threat model in the decision trail. Assets (accounts, money, personal data). Actors (anonymous visitor, signed-in user, another tenant, an attacker with a leaked token). Entry points (routes, webhooks, jobs, admin pages). Trust boundaries. The worst outcome. Run **interrogate** with it attached, per `../references/interrogate-triggers.md`.
2. Authorize on the server for every request. Scope each query by the owner or tenant id. A hidden button is not access control. Write the test that user A cannot read, change, or delete user B's record.
3. Use the auth provider's library for sessions and passwords. Do not write your own crypto. Sessions are `httpOnly`, `Secure`, `SameSite` cookies, rotate on login, and are invalidated server-side on logout. Tokens never go in URLs or logs. If you hash passwords yourself, use argon2id or bcrypt.
4. Treat input as hostile at the boundary, per **principle-boundary-discipline**. Parse it with a schema, use parameterized queries, escape output, add CSRF protection to cookie-authenticated writes, and rate-limit login, signup, password reset, and public webhooks.
5. Payments are sandbox-only for agents. Build and test every payment path in the provider's test mode or sandbox, with its test cards or sandbox accounts. Agents never hold, read, or set live payment keys, and never make a live charge or refund. The owner puts the live keys and the live webhook secret into production, through **wizard**, per `secrets-and-env.md`. Pick the provider and read its row in [`../references/payment-providers.md`](../references/payment-providers.md) before writing code. Lemon Squeezy is the default. PayPal and Paddle are covered too.
6. Keep test and live apart in code. The provider's mode comes from the environment, never from a code path. Development, CI, and preview use sandbox keys and the sandbox API base. Where the key shows its mode, assert it at startup. Paddle sandbox keys contain `_sdbx`, for example. Refuse to boot outside production with a live key, and in production with a sandbox key.
7. Never trust the client for a price or a plan. Create checkouts on the server from the provider's product or price id, and read amounts and status from the webhook or the API.
8. Verify every webhook signature over the raw body before parsing it, with a constant-time compare, using the scheme in the provider's row. Prove it in sandbox with the real sandbox signing secret. Write tests for a valid signature, a tampered body, a wrong secret, and a missing header. Where the provider signs a timestamp, also test a stale one.
9. Make the handler idempotent. When the provider sends an event id (PayPal's `id`, Paddle's `event_id`), store it under a unique constraint and skip repeats. Lemon Squeezy documents no event id, so make its handler idempotent by state. Upsert by the resource id, set access from the resource's latest state (fetched from the API when in doubt), and store a hash of the raw body to skip exact redeliveries. Return 2xx fast and do slow work in a job, inside the provider's response window. See `retries-concurrency-idempotency.md`.
10. Map payment and subscription status to access in one function. Test it with a table of every status the provider sends. Decide what refunds, cancellations, failed renewals, and disputes do, and log each change.
11. Prove each payment path in sandbox, end to end with **control-ui**: a successful purchase, a declined card, a renewal, a failed renewal, a cancellation, a refund, and a dispute or chargeback. For each one, the webhook arrives, passes signature verification, is processed once (including after the provider's resend), and changes access as the table says. Drive a path with a test checkout when you can, and with the provider's simulator or resend when you cannot. Simulated events may not be verifiable the way real ones are. The provider row says when.
12. Close sandbox gaps without real money. For a path the provider's sandbox cannot produce (the row's known gaps), write a handler test from a documented example payload, signed with a test secret. Then list the path under Attention as an owner check. The owner decides whether and how to verify it in live, and does it by hand. Agents never make a live charge to close a gap. Live charges stay on poteto-mode's Always-pause list as a safety net, and no step here calls for one.
13. Hand the owner a go-live checklist, and do not run it yourself.
    - The live keys and live webhook secret are set in production only.
    - The live webhook endpoint points at the production URL and subscribes to the events the handler expects.
    - The live product and price ids are mapped, if the provider keeps separate test and live catalogs.
    - The alerts in `observability.md` fire on a failed or missing payment webhook.

**Reply:** the threat model, each negative test and its result, the sandbox evidence for each payment path, the gaps handed to the owner, and the go-live checklist.
