### Auth, payments, and security

**You own the trust boundary. Write down what an attacker wants, then prove they cannot get it. Prove payments in the provider's sandbox, never with real money.**

1. Write a five-line threat model in the decision trail. Assets (accounts, money, personal data). Actors (anonymous visitor, signed-in user, another tenant, an attacker with a leaked token). Entry points (routes, webhooks, jobs, admin pages). Trust boundaries. The worst outcome. Run **interrogate** with it attached, per `../references/interrogate-triggers.md`.
2. Authorize on the server for every request. Scope each query by the owner or tenant id. A hidden button is not access control. Write the test that user A cannot read, change, or delete user B's record.
3. Use the auth provider's library for sessions and passwords. Do not write your own crypto. Sessions are `httpOnly`, `Secure`, `SameSite` cookies, rotate on login, and are invalidated server-side on logout. Tokens never go in URLs or logs. If you hash passwords yourself, use argon2id or bcrypt.
4. Treat input as hostile at the boundary, per **principle-boundary-discipline**. Parse it with a schema, use parameterized queries, escape output, add CSRF protection to cookie-authenticated writes, and rate-limit login, signup, password reset, and public webhooks.
5. Payments are sandbox-only for agents. Build and test every payment path in the provider's test mode or sandbox, with its test cards or sandbox accounts. Agents never hold, read, or set live payment keys, and never make a live charge or refund. A human puts the live keys and the live webhook secret into production, through **wizard**, per `secrets-and-env.md`. Choose the provider with the project's maintainer, and read its section in [`../references/payment-providers.md`](../references/payment-providers.md) before writing code. That file covers Lemon Squeezy, Paddle, PayPal, and Stripe, and names a merchant-of-record option for sellers whose country a provider does not serve.
6. Keep test and live apart in code. The provider's mode comes from the environment, never from a code path. Development, CI, and preview use sandbox keys and the sandbox API base. Where the key shows its mode, assert it at startup. Paddle sandbox keys contain `_sdbx`, for example. Refuse to boot outside production with a live key, and in production with a sandbox key.
7. Never trust the client for a price or a plan. Create checkouts on the server from the provider's product or price id, and read amounts and status from the webhook or the API.
8. Verify every webhook before acting on it, with the provider's own scheme. Use its official library when there is one.
   - **HMAC schemes.** Compute the HMAC over the exact raw body, never a re-serialized one, and compare with a constant-time compare. Lemon Squeezy signs the raw body with HMAC-SHA256 in `X-Signature`. Paddle signs `<ts>:<raw body>` in `Paddle-Signature`, with a five-second default tolerance on `ts`. Stripe signs `<t>.<raw body>` in `Stripe-Signature`, and its libraries default to a five-minute tolerance.
   - **PayPal** is asymmetric, not an HMAC. Call the verify-webhook-signature API with the `PAYPAL-*` headers, the configured `webhook_id`, and the event exactly as received, or self-verify against the certificate at `PAYPAL-CERT-URL`.
   - **Tests.** Prove it in sandbox with the real sandbox secret or webhook id. Write tests for a valid signature, a tampered body, a wrong secret, and a missing header. Where the scheme signs a timestamp, also test a timestamp outside the tolerance.
9. Make the handler idempotent and order-safe.
   - **Providers with an event id** (Paddle `event_id`, PayPal `id`, Stripe `id`). Record the id under a unique constraint in the same transaction as the state change, and skip a repeat. Delivery order is not guaranteed. Store the time each resource was last changed, from Paddle's `occurred_at` or the resource itself, and ignore an older event. Or fetch the resource's current state from the API, and set access from that.
   - **Lemon Squeezy** documents no event id. Make its handler idempotent by state. Upsert by the resource id, and set access from the resource's current state, fetched from the API when in doubt. To skip exact redeliveries, write a hash of the raw body under a unique constraint in the same database transaction as the upsert. A hash stored before the upsert commits would drop a retry of a delivery that failed halfway. Treat a duplicate-hash violation as already processed.
   - Return 2xx inside the provider's response window, and do slow work in a job. See `retries-concurrency-idempotency.md`.
10. Map payment and subscription status to access in one function. Test it with a table of every status the provider sends. Decide what refunds, cancellations, failed renewals, and disputes do, and log each change.
11. Prove each payment path in sandbox, end to end with **control-ui**. The paths are a successful purchase, a declined card, a renewal, a failed renewal, a cancellation, a refund, and a dispute where the sandbox supports one.
    - **What to check.** For each path, the webhook arrives, passes verification, is processed once, and changes access as the table says.
    - **Repeats and order.** Prove both with real sandbox deliveries, by failing the handler once to force a retry or by resending from the dashboard. A simulator may send an event only once, and some simulator events cannot be verified the way real ones are.
    - **How to drive each path.** Use a sandbox checkout with the provider's test cards first. Use the simulator for events a checkout cannot produce. Use a sandbox-only API, such as PayPal's dispute methods or Stripe's dispute test cards, where the provider's section names one.
12. Close sandbox gaps without real money. For a path the provider's sandbox cannot produce (its "Not documented" items), write a handler test from the provider's documented example payload, signed or verified the way the provider's section describes. Then list the path under Attention as a maintainer check. A human decides whether and how to verify it in live, and does it by hand. Agents never make a live charge to close a gap. Live charges stay on poteto-mode's Always-pause list as a safety net, and no step here calls for one.
13. Hand the maintainer a go-live checklist, and do not run it yourself.
    - The live keys and live webhook secret or webhook id are set in production only.
    - The live webhook endpoint points at the production URL and subscribes to the events the handler expects.
    - The live product and price ids are mapped, if the provider keeps separate test and live catalogs.
    - The alerts in `observability.md` fire on a failed or missing payment webhook.

**Reply:** the threat model, each negative test and its result, the sandbox evidence for each payment path, the gaps handed to the maintainer, and the go-live checklist.
